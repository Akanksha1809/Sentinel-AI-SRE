- **Three real bugs found only by running live, repeatedly, under real timing** (none security-relevant — all three are in the actuator's fault-forwarding path or the demo harness's own state management, not in any authorization/validation/guard boundary):
  1. **Actuator crash on a momentarily-unreachable replica.** `_forward_chaos` (used by both chaos injection and chaos clearing) let an unhandled `httpx.TransportError` to one replica abort the whole request — hit live when a baseline-reset deploy had just replaced both replicas and the very next call tried to clear chaos on them before their HTTP server had bound. Fixed: a per-replica try/except that records `{"status": null, "error": ...}` for that one replica instead of failing the fan-out; demo client's `clear_chaos` also made best-effort (`contextlib.suppress`). Regression test: `services/actuator/tests/test_api.py::TestFaultForwarding::test_one_unreachable_replica_does_not_fail_the_whole_fan_out`.
  2. **Stale incidents silently absorbed the next scenario's alert.** `reset_active_incidents` filtered on `active=True`, but `IncidentService._recently_resolved` (the reopen-within-window check) matches on `status == resolved` alone — a `resolved`-but-not-yet-`closed` incident from the previous run is still reopen-eligible even though it isn't "active". `wait_for_incident`'s `opened_at >= started_at` check then never matched, since the "new" alert just reopened the old incident instead. Fixed: resolve + close every not-yet-`closed` incident for the service, not just active ones.
  3. **Evidence correlation misattributed root cause when scenarios ran close together — two distinct issues, one a real `MockProvider` bug now fixed, one an inherent property of the evidence window.**
     - **Cross-alert-type contamination (actual bug, fixed).** `MockProvider` checked deployment correlation (`corr["score"] >= 0.6`) *before* any alert-type-specific evidence, with nothing tying the winning deployment candidate to the alert that actually fired. Caught live: a `ShopApiMemoryPressure` incident (scenario A, no deployment involved at all) got investigated shortly after scenario C's config deployment, which scored 0.77 — well clear of the threshold — purely on `time_factor` (recently deployed), even though `rollback-deployment` doesn't even list `ShopApiMemoryPressure` in its own `applies_to_alerts`. The mock recommended `rollback-deployment` for a memory-pressure incident. This is a genuine defect, not a demo-chaining artifact — it could misfire in real usage too, any time an unrelated-but-recent deployment happens to score well against a resource-pressure incident. Fixed in `src/sentinel/investigation/providers.py`: a new `_applies_to_alerts` gate reads the candidate runbook's own `applies_to_alerts` (already on the schema, just never consulted) and refuses the deployment-correlation branch when the incident's alertnames don't overlap it. Regression test: `tests/unit/test_investigation.py::TestMockProvider::test_stale_unrelated_deployment_does_not_outrank_memory_pressure` (fails without the fix, confirmed before committing it).
     - **Same-alert-type weak-signal competition (inherent, not a bug — mitigated by test ordering).** Scenario C's own signal is intrinsically weak even in isolation — a crash-loop (`POOL_SIZE=0`) never completes a request, so `metric_factor` (share of 5xx responses) is structurally 0, and very few log lines get written before each restart, so `log_factor` is low too (measured: C's own deployment scored **0.435** against the mock's 0.6 threshold). Both `ShopApiCrashLooping` (C) and `ShopApiHighErrorBurnRate` (B) are in `rollback-deployment`'s `applies_to_alerts`, so the new gate above doesn't separate them — a stale scenario-B deployment still within the 60-minute `CHANGE_LOOKBACK` window can legitimately outscore C's own weak signal (measured: 0.695 vs 0.435), binding the "rollback" to the wrong historical deployment record (so `target_config_revision` is never set, the fix is a no-op, and verification correctly fails — `restarts_in_window` kept climbing through the sampling window: 12 → 15 → 17). This is correct behavior for the evidence window's actual design (a deployment an hour ago can be the real cause of a real incident) colliding with synthetic fault injection faster than any real incident history would produce. Resolution: `tests/e2e/test_scenarios.py` runs scenario C first; documented in `docs/troubleshooting.md`.

## What exists (Phase 6)
- `src/sentinel/domain/actions.py`: `ActionRequest` state machine (`proposed → pending_approval → approved → executing → verifying → succeeded`, with `rejected/expired/failed/verification_failed/cancelled` terminals; a failed verification never auto-retries — a fresh proposal is required).
- `sentinel.remediation.policy`: `PolicyEngine` — required-approval runbooks always need a human; a hypothetical `policy_auto` runbook can self-approve, gated by a cooldown (falls back to approval if recently executed) and an incident-wide rate limit.
- `sentinel.remediation.service` (`ActionService`): propose (idempotent by `sha256(incident|runbook|params)`; policy-decided initial status; rate-limited), approve/reject (role-gated, replay-protected — refuses if the runbook's sha256 changed since proposal), expiry (lazy on decide + a periodic worker sweep), full audit + timeline on every transition.
- `sentinel.remediation.actuator_client`: `HttpActuatorClient` (classifies actuator responses into terminal `ActuatorError` vs retryable `ActuatorUnavailableError`) and `DryRunActuatorClient` (forces every call's `dry_run=true`, used when the global `SENTINEL_EXECUTION_MODE=dry_run`, the default).
- `sentinel.remediation.execution` (`ExecutionService`): locks the action row, calls the actuator with bounded internal retries (transient only; terminal fails immediately, no retry), records every attempt, advances to `verifying` and enqueues the verify job on success.
- `sentinel.remediation.verifier` (`VerificationService`): after `settle_s`, samples the runbook's checks every `interval_s` for up to `window_s`; succeeds on `consecutive` all-pass samples in a row, fails if the window runs out; a failed query or empty result **counts as a failed sample**, never as a pass.
- Migration 0004: `action_requests`, `approvals`, `action_executions`, `verifications` (app role: UPDATE allowed only on `action_requests`; the rest are insert-only).
- Investigations auto-propose their accepted actions (still gated by approval) — `InvestigationService(..., actions=...)`.
- API: `POST/GET /incidents/{ref}/actions`, `GET /actions/{id}`, `POST /actions/{id}/approve|reject` (Approver role).
- Compose: `sentinel-worker` joins the `app` network and gets the `actuator_token` secret to reach the actuator; `SENTINEL_EXECUTION_MODE` (`dry_run` default / `live`).
